# 简历项目测试与性能证据

首次完整基准：2026-10-30（Asia/Shanghai）

最新功能与证据回归：2026-11-01（Asia/Shanghai）

## 1. 结论

项目的功能链路可以正常运行，POI 空间查询的 GiST 索引优化、MVT Redis 缓存和
多景点顺序优化均有实测证据。与此同时，10 点完整游览规划仍存在明显性能瓶颈：
Held-Karp 本身很快，主要时间消耗在成本矩阵计算以及按访问顺序重复生成每一段
pgRouting 路线和 WKT 几何。

因此，简历可以量化空间查询与“顺序优化算法”的效果，但不能把算法耗时写成整个
游览规划接口的端到端耗时。

## 4. GiST 空间查询优化

方法：对同一条 500 米范围 PostGIS 查询执行 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，
预热一次后记录 7 次执行时间的中位数。索引组强制允许 Index/Bitmap Scan 并关闭
Seq Scan；基线组关闭 Index/Bitmap Scan 并强制 Seq Scan。两组使用相同连接、SQL、
参数和数据。

| 指标 | GiST 索引计划 | 顺序扫描基线 |
| --- | ---: | ---: |
| 稳态 P50 | 0.056 ms | 77.515 ms |
| 执行计划 | Index/Bitmap Index Scan | Seq Scan |

本次稳态测量加速约 1,384 倍。首次单次观测为 1.486 ms 对 69.692 ms，约 46.9 倍，
说明冷/热缓存状态会显著影响绝对时间。因此简历应写清“同机、同库、500 米范围查询、
稳态 P50”，不要把该数字泛化为所有 POI 查询。

## 5. MVT Redis 缓存

对一个真实非空 `base` 瓦片（z=14, x=4500, y=10062，278 bytes）连续请求两次：

| 请求 | 耗时 |
| --- | ---: |
| 首次观测 | 249.07 ms |
| 重复请求 | 5.80 ms |

本次观测加速约 42.9 倍。该结果证明同一数据版本、同一瓦片键的重复请求能避开数据库
MVT 生成。由于缓存 TTL 为 7 天，脚本重复执行时“首次观测”可能已经是缓存命中；如需
正式压测，应在隔离测试环境中使用新的数据版本，而不是清理共享 Redis。

## 6. 道路离线 LOD 量化基准

基准绕过 Redis，在 z=2～7 每个层级选择 3 个行政区内可见道路最密集的瓦片，共
18 个瓦片。原始分支与 LOD 分支使用相同的 z/x/y、道路最小可见层级、广州行政区
裁剪、MVT extent/buffer 以及 `id`、`road_type` 字段。每个瓦片预热 2 次，再交替执行
两个分支各 7 次，避免把数据库热缓存次序或字段差异误算成 LOD 收益。

原始分支在请求时完成行政区裁剪与 MVT 编码；LOD 分支读取已离线聚合、简化和预裁剪的
`road_edge_lod_2/4/6`。结果如下：

| 层级 | 原始 P50 | LOD P50 | P50 提升 | 瓦片字节减少 | 顶点减少 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| z2 | 1,508.05 ms | 7.39 ms | 204.21x | 91.8% | 81.6% |
| z3 | 1,048.57 ms | 6.52 ms | 160.74x | 91.0% | 81.5% |
| z4 | 527.00 ms | 2.11 ms | 249.80x | 91.3% | 85.4% |
| z5 | 388.07 ms | 2.76 ms | 140.58x | 91.3% | 85.5% |
| z6 | 173.31 ms | 1.11 ms | 155.57x | 88.5% | 85.5% |
| z7 | 110.40 ms | 0.90 ms | 123.35x | 88.8% | 84.4% |
| 汇总（126 次/分支） | 409.46 ms | 2.30 ms | 178.45x | 91.2% | 83.0% |

18 个瓦片的 MVT 总大小由 1,570,564 bytes 降至 138,553 bytes，道路要素数由
47,700 降至 474，MVT 顶点数由 236,613 降至 40,284。该结果证明低层级道路离线
聚合、简化与预裁剪显著降低在线空间运算和传输量；它不包含 Redis 缓存收益，也不代表
z8 及以上层级，因为 z8 起服务按设计切换回原始道路。

本基准验证两组瓦片均非空，但没有自动判断地图视觉质量、道路连通观感或不同类别道路的
样式表达。正式发布前仍应补充截图回归或人工视觉验收，不能只凭体积更小判断 LOD 正确。

## 7. 多景点规划分段耗时

使用真实道路中点构造 10 个可达游览点，步行 FASTEST、闭环、AUTO 算法：

| 阶段 | 结果 |
| --- | ---: |
| pgRouting 有向成本矩阵 | 1,416.421 ms |
| Held-Karp 顺序优化 P50（51 次） | 0.412 ms |
| 完整规划 P50（3 次，含 10 段路线与几何） | 10,348.749 ms |
| 算法结果 | HELD_KARP，optimal=true |

结论：Held-Karp 的顺序求解不是当前瓶颈；完整接口慢在成本矩阵以及逐段重复执行
pgRouting 和 WKT 几何拼接。后续若优化完整接口，应优先考虑一次 SQL 批量返回所有
相邻段路线、复用路网图或缓存成本矩阵，而不是继续微调 Held-Karp。

## 8. POI 网格缓存基准

基准使用真实 PostGIS、Redis 和 POI 数据，在 POI 最密集网格附近分别执行直接数据库
圆形查询、独立前缀的冷缓存查询以及热缓存查询。每个缓存实验使用临时 Key，并在结束
后精确删除，不影响业务缓存。

本轮首次基准时的配置为 `poi-spatial-zoom=4`，在 262,144 m 的局部世界范围内对应约
16,384 m 的网格边长。实测如下：

| 半径 | 返回数量 | 网格数 | 冷缓存 | 热缓存 P50 | 数据库 P50 | 热缓存效果 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 500 m | 46 | 1 | 4,079.84 ms | 26.08 ms | 1.96 ms | 0.08x，反而更慢 |
| 2,000 m | 3,442 | 1 | 294.90 ms | 23.30 ms | 24.98 ms | 1.07x |
| 8,000 m | 8,182 | 4 | 245.63 ms | 37.67 ms | 51.30 ms | 1.36x |

并发实验每轮先删除独立测试前缀下的目标网格 Key，再同时放行 8 个同网格请求；连续
执行 50 轮，400 个请求共触发 50 次数据库范围查询，并逐轮断言恰好回源 1 次。数据库
回源相对每请求一次减少 87.5%，每轮 8 个请求整体完成时间 P50 为 131.89 ms、P95 为
419.08 ms。这证明单 JVM、同一空间网格、Redis 正常场景下，锁内二次检查可以稳定合并
并发冷请求，而不只是一次偶然观测。

该结论不能直接外推到多实例部署：当前 `fillLock` 是 JVM 内对象锁，不同实例仍可能同时
回源；不同网格、Redis 故障和更高并发也未包含在本轮实验中。并且 z=4 网格过粗，小范围
查询需要反序列化整个高密度网格，性能明显差于 GiST 查询，不能在简历中宣称当前配置对
所有 POI 查询都有明显加速。

进一步保持实现不变，仅比较网格层级：

| 半径 | z=4 | z=6 | z=8 | z=9 | 数据库 P50 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 500 m | 32.85 ms | 7.17 ms | 4.18 ms | **1.52 ms** | 4.99 ms |
| 2,000 m | 20.69 ms | 14.04 ms | **13.22 ms** | 13.40 ms | 22.58 ms |

z=9 对 500 m 查询约加速 3.29 倍，对 2,000 m 查询约加速 1.69 倍；但 2,000 m
查询需要读取 72 个网格 Key。项目当前已据此将默认配置调整为 `z=9`，并保留
`CACHE_POI_SPATIAL_ZOOM` 环境变量便于按实际查询半径与 Redis 内存占用继续调优。
若大视口查询较多，更合理的后续方案仍是多层级网格，而不是让所有查询固定使用同一个 zoom。

## 9. 简历推荐改写

空间查询条目建议写成：

> 基于 3.4 万条有效 POI 建立 GiST 空间索引并优化 PostGIS 范围查询；在同机同库
> 500 米查询基准中，稳态 P50 由 77.5 ms 降至 0.06 ms，并通过 EXPLAIN ANALYZE
> 验证执行计划由 Seq Scan 切换为 Bitmap/Index Scan。

路径规划条目建议写成：

> 将最短路计算迁移至 pgRouting，基于有向路网成本矩阵实现 Held-Karp 精确求解与
> 最近邻 + 2-opt 启发式求解；10 个可达游览点下，真实成本矩阵生成约 1.42 s，
> Held-Karp 顺序优化 P50 为 0.41 ms，并通过自动化测试验证固定起终点、闭环、
> 单行方向成本及不可达场景。

不要写“10 点游览规划耗时 0.41 ms”，因为完整接口实测 P50 为约 10.35 s。

缓存条目可补充为：

> 对 MVT 使用带数据版本的 Redis Cache Aside 缓存，避免数据更新时扫描删除旧键；
> 实测同一非空瓦片由首次观测 249 ms 降至重复请求 5.8 ms。

道路 LOD 条目建议写成：

> 针对低层级道路设计离线聚合、几何简化与行政区预裁剪；在 z2～z7 共 18 个道路密集
> 瓦片、每瓦片 7 次的无缓存对照中，MVT 生成 P50 由 409.5 ms 降至 2.3 ms，提升约
> 178 倍，瓦片体积减少 91.2%，顶点数减少 83.0%。

若希望更保守，也可以写“提升 120 倍以上”，因为六个被测层级中最低提升为 123.35 倍。

POI 网格缓存当前更适合写成设计与并发正确性成果：

> 将 POI 按固定空间网格缓存至 Redis，使用 MGET 批量读取相交网格，未命中网格合并为
> 一次 PostGIS 范围查询；通过锁内二次检查合并并发冷请求，单实例同网格冷缓存场景下，
> 连续 50 轮共 400 个请求仅回源数据库 50 次，回源减少 87.5%，并通过数据版本化 Key
> 实现无扫描逻辑失效。

当前默认配置已调整为 z=9，因此可以在明确测试条件的前提下补充：“在当前广州证据库、
固定 z=9 网格和热缓存基准中，500 m 查询 P50 由数据库路径 4.99 ms 降至 1.52 ms，
约提升 3.29 倍”。该数字不能外推到冷缓存、大视口或多实例场景。

## 10. 一键复现

确保 PostgreSQL/PostGIS/pgRouting、Redis 和后端已启动，然后在后端仓库执行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_resume_evidence.ps1
```

真实数据库证据测试也可单独执行：

```powershell
mvn -pl nav-server -am `
  '-Dtest=ResumeEvidenceIntegrationTest' `
  '-Dresume.evidence=true' `
  '-Dsurefire.failIfNoSpecifiedTests=false' `
  test
```

证据测试默认不随普通 `mvn test` 运行，避免 CI 或没有本地空间数据库的环境误执行
约一分钟的真实性能测试。

POI 网格缓存基准可单独执行：

```powershell
mvn -pl nav-server -am `
  '-Dtest=PoiGridCacheEvidenceIntegrationTest' `
  '-Dpoi.cache.evidence=true' `
  '-Dsurefire.failIfNoSpecifiedTests=false' `
  test
```

只运行 50 轮并发冷请求实验：

```powershell
mvn -pl nav-server -am `
  '-Dtest=PoiGridCacheEvidenceIntegrationTest#shouldCoalesceConcurrentColdMissesIntoOneDatabaseLoad' `
  '-Dpoi.cache.evidence=true' `
  '-Dsurefire.failIfNoSpecifiedTests=false' `
  test
```

道路 LOD 量化基准可单独执行：

```powershell
mvn -pl nav-server -am `
  '-Dtest=RoadLodEvidenceIntegrationTest' `
  '-Dlod.evidence=true' `
  '-Dsurefire.failIfNoSpecifiedTests=false' `
  test
```

LOD 基准只读访问 PostGIS，当前机器约需 2 分钟。上述真实性能测试均通过系统属性显式
开启，普通 `mvn test` 只会将其标记为跳过。
